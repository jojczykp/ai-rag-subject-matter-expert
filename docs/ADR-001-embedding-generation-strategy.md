# ADR-001: Embedding Generation Strategy

## Status

Accepted.

## Context

The application uses retrieval-augmented generation. Static subject documents
are split into chunks, indexed, and later retrieved for each chat request.
Semantic retrieval requires embeddings for both stored document chunks and user
queries.

The embedding strategy must support online cloud models, local server models,
and future fully offline usage. It also affects database schema, startup
indexing, model configuration, test design, and privacy expectations.

The key constraint is that document chunk embeddings and query embeddings must
be generated by the same embedding model, or at least by compatible models in
the same embedding space. Otherwise vector similarity results are unreliable.

## Decision

Use a dedicated embedding model catalog for retrieval. Embedding models are
configured separately from chat models, and retrieval uses the embedding model
selected in the chat request when provided.

The selected chat model remains user-controlled per request. The selected
embedding model is responsible for:

- [ ] generating embeddings for bundled document chunks during indexing
- [ ] generating embeddings for user queries during retrieval
- [x] exposing embedding model metadata needed to validate stored vectors

Document chunk embeddings and query embeddings must use the same embedding
model metadata. Chat models receive retrieved text chunks and do not need to
share the embedding model or embedding vector space.

Prefer a local embedding model when available, because it keeps document
indexing and query embedding generation independent from cloud providers. Use
keyword or full-text retrieval as a temporary fallback only if embedding support
is not implemented yet. The preferred local runtime is documented in
[ADR-006: Local Embedding Runtime](ADR-006-local-embedding-runtime.md).

## Options Considered

### Option 1: Dedicated Embedding Model Configured Separately

Use dedicated embedding models for indexing documents and embedding user
questions, independent from the selected chat model.

Example:

```text
chat model: user chooses per request
embedding model: user can select from the configured embedding catalog
```

Benefits:

- [ ] Document embeddings and query embeddings use the same embedding space.
- [ ] Users can switch chat models without re-indexing documents.
- [ ] pgvector storage and lookup stay straightforward.
- [x] Tests can use predictable embedding model metadata.
- [ ] Cloud, local server, and embedded chat models can share retrieval logic.

Tradeoffs:

- [x] The application needs configured embedding models in addition to chat models.
- [ ] Startup/indexing must validate that stored embeddings match the configured
      embedding model metadata.

This is the selected option.

### Option 2: Use The Selected Chat Provider's Embedding Model

Use an embedding model from the same provider as the selected chat model.

Benefits:

- [ ] Provider-specific behavior stays grouped together.
- [ ] This may fit strict provider isolation requirements in the future.

Tradeoffs:

- [ ] Switching chat models may require separate stored embeddings per provider.
- [ ] Some chat providers may not expose suitable embedding models.
- [ ] Database schema and retrieval logic become more complex.
- [ ] Static documents may need repeated indexing for different model choices.

This is not recommended for the initial implementation.

### Option 3: Local Embedding Model For All Modes

Run a local embedding model and use it for online, local server, and offline
chat modes.

Examples:

- [ ] Ollama embedding model
- [ ] sentence-transformers model through a local service
- [ ] ONNX embedding model
- [ ] llama.cpp-compatible embedding model if suitable

Benefits:

- [ ] Document indexing and query embedding generation can stay local.
- [ ] Cloud chat providers receive only retrieved chunks, not the full document
      set.
- [ ] Offline mode can reuse the same retrieval pipeline.
- [ ] Privacy behavior is easier to explain.

Tradeoffs:

- [ ] Requires provisioning and operating a local embedding model.
- [ ] Local hardware affects indexing and retrieval latency.
- [ ] Packaging and licensing requirements must be documented.

This is a strong long-term direction and should be preferred when practical.

### Option 4: No Embeddings Initially, Keyword Or Full-Text Retrieval

Use keyword matching or PostgreSQL full-text search first, then add embeddings
later.

Benefits:

- [ ] Fastest path to an initial chat flow.
- [ ] No embedding model is required.
- [ ] Works fully offline immediately.
- [ ] Can be combined with vector search later as hybrid retrieval.

Tradeoffs:

- [ ] Semantic matching quality is weaker.
- [ ] Users need to ask questions using terms close to the source documents.
- [ ] Vector schema and embedding flow still need to be added later.

This is acceptable only as a temporary implementation step.

## Consequences

- [x] Store the embedding model id or version with indexed chunk embeddings.
- [x] Store embedding dimensions with indexed chunk embeddings.
- [x] Store the chunking strategy version used to create indexed chunks.
- [x] Re-index documents when configured embedding model metadata changes.
- [x] Re-index documents when embedding dimensions or chunking strategy changes.
- [x] Keep embedding generation separate from chat model selection.
- [x] Allow users to switch chat models without re-indexing documents.
- [ ] Keep `RelevantChunkRetriever` responsible for query embedding generation
      and vector lookup.
- [x] Use PostgreSQL + pgvector for vector storage and similarity search.
- [x] Add tests that prove document and query embeddings use compatible model
      metadata.
- [ ] Add integration tests for vector search with Testcontainers and pgvector.

## Future Considerations

- [ ] Add hybrid retrieval with full-text ranking plus vector similarity.
- [ ] Support optional multiple embedding indexes only if future requirements
      need runtime or provider isolation.
- [ ] Add operational documentation for local embedding model setup.
- [ ] Add offline embedding model packaging and license validation.
